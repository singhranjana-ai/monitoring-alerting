
# AWS EC2 Application Server Monitoring and Alerting
### Prometheus | Grafana | Node Exporter | Alertmanager | PagerDuty

## 1. Project Overview

This project implements an automated infrastructure monitoring and alerting solution for AWS EC2 application servers using open-source monitoring tools.

The monitoring solution uses AWS EC2 tags to identify application servers that need to be monitored.

The EC2 tag `node_server` is used as the identification criteria for selecting application servers where Node Exporter is installed.

Prometheus discovers the matching EC2 instances, collects their system metrics through Node Exporter, and stores the collected metrics for monitoring and analysis.

Grafana provides a centralized dashboard for visualizing server performance, while Alertmanager manages alerts generated by Prometheus and forwards incidents to PagerDuty.

### Key Objectives

- Monitor AWS EC2 application servers.
- Identify monitoring targets using EC2 tags.
- Automatically discover matching EC2 instances using Prometheus.
- Collect server metrics using Node Exporter.
- Monitor CPU, memory, disk and server availability.
- Visualize infrastructure performance using Grafana.
- Configure infrastructure alerting using Prometheus.
- Integrate PagerDuty for incident management and notifications.
- Automate installation and configuration using Bash scripts.
- Follow Linux security best practices using dedicated service users.

### Architecture Components

**1. AWS EC2 Application Servers**

Application servers are launched in AWS EC2.

Each application server that needs monitoring is assigned the EC2 tag `node_server` according to the configured tag key/value convention.

**2. Node Exporter**

Node Exporter is installed on the application servers.

It exposes Linux system metrics through port 9100.

Metrics include:

- CPU utilization
- Memory utilization
- Disk utilization
- Filesystem availability
- Network traffic
- System uptime

**3. Prometheus**

Prometheus runs on a centralized monitoring server.

It uses AWS EC2 service discovery to retrieve EC2 instance information and filters instances using the configured `node_server` tag.

It periodically scrapes Node Exporter metrics from matching instances.

**4. Grafana**

Grafana connects to Prometheus as its data source.

It displays server health and performance metrics using dashboards.

**5. Prometheus Alert Rules**

Prometheus evaluates alert rules for:

- Application server down.
- High CPU utilization.
- High disk utilization.

**6. Alertmanager**

Alertmanager receives firing alerts from Prometheus and manages alert routing, grouping, silencing and notification delivery.

**7. PagerDuty**

PagerDuty receives events from Alertmanager through its integration API.

PagerDuty creates incidents and notifies the configured responders according to the incident management and escalation policies.

| 9094 | Alertmanager | Optional HA clustering |

### Security Group Configuration

- Port 9100: Allow inbound access only from the Prometheus monitoring server.
- Port 9090: Restrict access to trusted administrators and internal components.
- Port 3000: Allow access only from trusted administrator IPs.
- Port 9093: Restrict access to trusted internal sources.
- Port 443: Allow outbound HTTPS communication to PagerDuty.
- Port 22: Restrict SSH access to administrator IP addresses.

Do not expose monitoring services publicly without appropriate security controls.

## 5. EC2 Tag-Based Server Discovery

### Objective

Automatically identify application servers that need monitoring based on their AWS EC2 tags.

### Process

1. Launch an application EC2 instance.
2. Install Node Exporter on the application server.
3. Assign the configured `node_server` EC2 tag.
4. Configure Prometheus EC2 service discovery.
5. Filter instances using the EC2 tag.
6. Discover their private IP addresses.
7. Scrape Node Exporter metrics on port 9100.

### Why use EC2 tags?

Without tag-based discovery, administrators may need to manually update Prometheus configuration whenever a new application server is launched.

With EC2 service discovery and tag filtering, matching instances can be discovered automatically.

This improves scalability and reduces manual configuration.

### IAM Permissions

The Prometheus server requires AWS permissions to describe EC2 instances.

Required permission:

```text
ec2:DescribeInstances
```

This permission can be provided through an IAM role attached to the Prometheus EC2 instance.

Avoid hardcoding AWS access keys in configuration files.

## 6. Prometheus EC2 Service Discovery

Example configuration:

```yaml
scrape_configs:

  - job_name: 'node_server'

    ec2_sd_configs:
      - region: us-east-1
        port: 9100
        filters:
          - name: instance-state-name
            values:
              - running

    relabel_configs:

      - source_labels: [__meta_ec2_tag_Name]
        regex: node_server
        action: keep

      - source_labels: [__meta_ec2_private_ip]
        target_label: instance

      - source_labels: [__meta_ec2_instance_id]
        target_label: ec2_instance_id
```

**Important:** This example assumes your actual AWS tag is `Name=node_server`. If `node_server` is the tag key instead, change the source label to `__meta_ec2_tag_node_server` and adjust the regex to match its value.

The `port: 9100` setting tells Prometheus which Node Exporter port to scrape.

The `keep` relabeling action ensures that only matching EC2 instances remain as monitoring targets.

EC2 discovery requires suitable IAM permissions and network connectivity between the Prometheus server and the application servers.

## 7. Prometheus Metrics Collection

Prometheus periodically scrapes metrics from the discovered Node Exporter endpoints.

Example:

```text
Application Server Private IP: 10.0.1.25
Node Exporter Port: 9100

Metrics Endpoint:

http://10.0.1.25:9100/metrics
```

Example Prometheus settings:

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s
```

This configuration makes Prometheus scrape metrics every 15 seconds and evaluate alert rules every 15 seconds.

### Verification

Access:

```text
http://PROMETHEUS-IP:9090/targets
```

Expected result:

```text

Endpoint: PRIVATE-IP:9100
State: UP
```

## 8. Grafana Dashboard

Grafana is configured with Prometheus as its data source.

The dashboard provides centralized monitoring of discovered application servers.

### Dashboard Panels

| Panel | Monitoring |
|---|---|
| CPU Utilization | CPU usage percentage |
| Memory Utilization | RAM consumption |
| Disk Utilization | Filesystem usage |
| Network Traffic | Network receive and transmit |
| Server Availability | UP/DOWN status |
| System Uptime | Server running duration |

### Useful PromQL Queries

**Server Availability**

```promql
up{job="node_server"}
```

**CPU Utilization**

```promql
100 - (
  avg by (instance) (
    rate(node_cpu_seconds_total{
      job="node_server",
      mode="idle"
    }[5m])
  ) * 100
)
```

**Memory Utilization**

```promql
(
  1 -
  node_memory_MemAvailable_bytes{
    job="node_server"
  }
  /
  node_memory_MemTotal_bytes{
    job="node_server"
  }
) * 100
```

**Disk Utilization**

```promql
(
  1 -
  node_filesystem_avail_bytes{
    job="node_server",
    mountpoint="/"
  }
  /
  node_filesystem_size_bytes{
    job="node_server",
    mountpoint="/"
  }
) * 100
```

**Network Receive Traffic**

```promql
rate(node_network_receive_bytes_total{
  job="node_server"
}[5m])
```

**Network Transmit Traffic**

```promql
rate(node_network_transmit_bytes_total{
  job="node_server"
}[5m])
```

## 9. Prometheus Alerting Scenarios

This project focuses on three infrastructure alert scenarios.

### Alert 1: Application Server Down

Objective: Detect when an application server becomes unreachable.

PromQL:

```promql
up{job="node_server"} == 0
```

Expected behavior:

- Prometheus detects that the Node Exporter scrape has failed.
- The alert enters Pending state.
- After the configured duration, the alert becomes Firing.
- Prometheus forwards the alert to Alertmanager.
- Alertmanager sends the incident event to PagerDuty.

Note: This detects monitoring endpoint availability, not necessarily the health of the application process itself.

### Alert 2: High CPU Utilization

Objective: Detect CPU utilization above 80%.

PromQL:

```promql
100 - (
  avg by (instance) (
    rate(node_cpu_seconds_total{
      job="node_server",
      mode="idle"
    }[5m])
  ) * 100
) > 80
```

Expected behavior:

- Prometheus continuously evaluates CPU usage.
- If CPU utilization remains above 80% for the configured duration, the alert fires.
- Alertmanager forwards the alert to PagerDuty.

### Alert 3: High Disk Utilization

Objective: Detect filesystem utilization above 80%.

PromQL:

```promql
(
  1 -
  node_filesystem_avail_bytes{
    job="node_server",
    mountpoint="/"
  }
  /
  node_filesystem_size_bytes{
    job="node_server",
    mountpoint="/"
  }
) * 100 > 80
```

Expected behavior:

- Prometheus evaluates filesystem utilization.
- When disk usage remains above the configured threshold, the alert fires.
- Alertmanager forwards the event to PagerDuty.

## 10. Prometheus and PagerDuty Integration

### Integration Flow

```text
Prometheus Alert Rules
         |
         v
    Alert Firing
         |
         v
    Alertmanager
         |
         v
   PagerDuty Integration
         |
         v
     HTTPS API
         |
         v
      PagerDuty
         |
         v
   Incident Created
         |
         v
 On-call Notification
```

### Configuration Process

1. Log in to PagerDuty.
2. Create or select an appropriate service.
3. Add a Prometheus-compatible Events API v2 integration.
4. Copy the integration routing key.
5. Configure the PagerDuty receiver in Alertmanager.
6. Configure Prometheus to send alerts to Alertmanager.
7. Validate the configuration.
8. Restart or reload the required services.
9. Trigger a test alert.
10. Verify incident creation in PagerDuty.

### Example Alertmanager Configuration

```yaml
global:
  resolve_timeout: 5m

route:
  receiver: pagerduty
  group_by:
    - alertname
    - instance
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h

receivers:
  - name: pagerduty
    pagerduty_configs:
      - routing_key: 'YOUR_PAGERDUTY_INTEGRATION_KEY'
        severity: '{{ .CommonLabels.severity }}'
        description: '{{ .CommonAnnotations.summary }}'
```

The integration key is a secret. Do not commit it to GitHub. Use a secure secrets-management method or a protected configuration file.

### Expected Results

- A server-down alert generates a PagerDuty incident.
- A high-CPU alert generates a PagerDuty incident.
- A high-disk alert generates a PagerDuty incident.
- Resolved alerts can automatically resolve corresponding PagerDuty incidents when resolution events are enabled.

## 13. Testing and Validation

### Test 1: Server Availability

Stop Node Exporter on the application server:

```bash
sudo systemctl stop node_exporter
```

Expected result:

- Prometheus target becomes DOWN.
- InstanceDown alert fires after its configured duration.
- Alertmanager forwards the event to PagerDuty.

Restart Node Exporter:

```bash
sudo systemctl start node_exporter
```

Expected result: The target returns to UP and the alert resolves.

### Test 2: High CPU

Install stress-ng if required:

```bash
sudo dnf install stress-ng -y
```

Generate CPU load:

```bash
stress-ng --cpu 2 --timeout 180s
```

Expected result: CPU usage increases and the alert fires if the threshold remains exceeded for the configured duration.

### Test 3: High Disk

Use a dedicated test filesystem or test volume to simulate high disk utilization.

Avoid filling the production root filesystem.

Expected result: The disk alert fires when the configured threshold and duration are reached.

### Test 4: PagerDuty

Verify:

- PagerDuty receives the event.
- Incident is created.
- Correct severity is displayed.
- On-call responders receive notifications.
- Resolved alerts update the corresponding incident.

## 14. Security Best Practices

- Use IAM roles for EC2 discovery.
- Avoid hardcoding AWS access keys.
- Run monitoring services using dedicated Linux users.
- Avoid running services as root.
- Use private IP addresses for metrics collection.
- Restrict Node Exporter port 9100.
- Protect Grafana credentials.
- Protect PagerDuty integration keys.
- Never commit secrets to GitHub.
- Restrict monitoring interfaces through Security Groups.
- Regularly update monitoring components.
